# Load testing — TeamForge API

Tool: **Artillery** (`npx artillery@2`, nothing to install globally).
Config: `artillery.yml`. Requirement from PS1: **p95 latency < 200 ms**.

## What is being tested

Two scenarios run together for 40 s at ~30 virtual users/second
(~1,200 VUs total):

| Scenario | Weight | What it does |
| -------- | ------ | ------------ |
| Browse teams | 70% | `GET /api/teams`, then `GET /api/teams/:id` — the read traffic of everyone browsing during a deadline rush. |
| Join stampede | 30% | `POST /api/teams/:id/join` against ONE team (capacity 10) from a pool of 100 users. |

About the stampede numbers: capacity is capped at 10 and the owner holds
seat #1, so only 9 joins can ever return `200`. Every other join correctly
returns `409` ("Team is full" / "already a member"). That is **the race
working as designed**, reproduced under load — what matters is that
responses stay fast and there are **zero 5xx errors**. Exact correctness
(exactly 9 succeed, count ends at exactly 10, no duplicate members) is
proven by the Jest concurrency tests, not by the load run.

## Run it locally (one command)

```bash
node load/run-local.js
```

This starts a throwaway in-memory MongoDB, boots the real API against it,
prepares the users/team, runs Artillery, and writes:

- `report-local.json` — Artillery's full machine-readable report
- `results-local.txt` — short human summary incl. the measured p95

## Run it manually (e.g. against the deployed API)

```bash
# 1. Point prepare at the API and create the users + stampede team:
LOAD_BASE_URL=https://<deployed-api> node load/prepare.js

# 2. Run Artillery against the same target:
npx artillery@2 run load/artillery.yml --target https://<deployed-api>
```

`prepare.js` writes `load/context.json` (team id + user tokens);
`processor.js` reads it during the run to give each virtual user a token.
`context.json` contains throwaway load-test tokens only and is gitignored.

> **Proxy gotcha (this dev machine):** the VM sets `HTTP_PROXY` /
> `HTTPS_PROXY` for its egress proxy, and Artillery's HTTP engine honours
> them but not `NO_PROXY`. Point Artillery at a **local** target with
> those variables set and every request is sent to the proxy and dies
> (`ECONNRESET`). `run-local.js` strips them automatically; if you run
> Artillery by hand against localhost, do the same:
> `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY npx artillery@2 run ...`.
> For a **deployed** target from this machine, keep the variables —
> external traffic genuinely needs the proxy.
